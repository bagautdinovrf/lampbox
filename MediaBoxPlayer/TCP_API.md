# MediaBoxPlayer: TCP API v1 и задание на подключение MediaBoxManager

Документ предназначен для разработчика или агента, который будет реализовывать
клиент MediaBoxPlayer. Его можно передать целиком: контракт, алгоритм клиента,
ограничения и критерии приёмки приведены ниже без зависимости от истории чата.

Описана текущая реализация **MediaBoxPlayer 0.2.0**, **protocolVersion = 1**.
Разделы 1–8 описывают поведение сервера. Разделы 9–12 задают рекомендации и
требования к будущему клиенту. Рекомендации не означают, что такие механизмы
уже реализованы в MediaBoxManager.

## 1. Назначение и границы

MediaBoxPlayer — фоновый аудиоплеер без окна. Он работает службой Windows,
демоном под systemd в Linux или Android foreground service. MediaBoxManager
управляет работающим плеером **исключительно через TCP**: очередь, воспроизведение,
громкость, mute, повтор, позиция и чтение состояния.

Существующий Manager пока использует старый LampPlayer. Новый клиент должен
говорить с описанным здесь TCP API. Вызовы `lmplayer.exe`, чтение реестра/INI,
shell-команды, Android Intent и файловый обмен не являются транспортом команд
нового плеера.

Служба должна быть установлена и запущена до подключения. Запустить остановленный
процесс через его собственный TCP-порт невозможно. Команда `stop` останавливает
музыку и оставляет службу доступной для `play`.

### Что уже есть

- 13 команд: `status`, `load`, `enqueue`, `play`, `pause`, `stop`, `next`,
  `previous`, `seek`, `volume`, `mute`, `repeat`, `clear`.
- Ответ с актуальным состоянием после каждой обработанной команды движка.
- Одна общая очередь и один системный аудиовыход по умолчанию.
- Одинаковый сетевой протокол на Windows, Linux и Android.

### Чего в v1 нет

- HTTP, WebSocket, встроенного TLS, discovery, `hello`, `login`, `ping`.
- Подписок, push-событий, серверного heartbeat или журнала событий через API.
- Защиты от повторного выполнения по `id`, транзакций нескольких команд,
  версии состояния, идентификатора запуска процесса или блокировки одного Manager.
- Передачи аудиофайлов, потоковых URL, сканирования медиатеки, выбора аудиоустройства,
  удаления одной записи очереди, перестановки записей или прямого `playIndex`.
- Команд shutdown/restart службы, удалённого изменения адреса/порта/токена.
- Исполнения `schedule-v1`, видео, shuffle и сохранения runtime на диск.

Не отправляйте предполагаемые команды из этого списка: они не реализованы.
Расписание и доставка медиафайлов — отдельные задачи.

## 2. Подключение и доступ

| Параметр | Значение |
| --- | --- |
| Транспорт | Обычный TCP, постоянное двустороннее соединение |
| Адрес сервера по умолчанию | `127.0.0.1` |
| Порт по умолчанию | `17655` |
| Кодировка | UTF-8 |
| Формат | Один JSON-объект на строку, завершение байтом LF (`0x0A`) |
| Аутентификация | Поле `token` в каждом запросе |
| Версия протокола | Число `1` в поле `protocolVersion` каждого запроса и ответа |

Manager хранит параметры `host`, `port`, `token` для подключения. `host` — адрес
машины плеера; в клиенте он может быть IP или DNS-именем. Серверный параметр
`--listen` принимает IP-адрес привязки. Например, при первоначальной настройке:

```sh
MediaBoxPlayer --data-dir /srv/mediabox/player --listen 192.168.10.25 --port 17655
```

Привязка к localhost не даёт прямого доступа с другой машины. Для сети задайте
доступный интерфейс и настройте сетевой доступ либо используйте туннель. Адрес
`0.0.0.0` означает привязку ко всем IPv4-интерфейсам; клиент подключается к реальному
адресу машины, а не к `0.0.0.0`.

Токен — 64 строчных шестнадцатеричных символа, созданных плеером случайно при
первом запуске. Он сохраняется в `<data-dir>/control.token`. Перевод строки
в конце файла не входит в токен. В стандартных развёртываниях:

| Платформа | Где хранится токен |
| --- | --- |
| Windows, предоставленный скрипт службы | `%ProgramData%\MediaBox\MediaBoxPlayer\control.token` |
| Linux, предоставленный пользовательский systemd unit | `/etc/mediabox/mediaboxplayer/control.token` |
| Android | `files/mediabox/mediaboxplayer/control.token` в закрытом каталоге APK |

При другой настройке путь определяется `--data-dir`. Токен передаётся Manager
при первоначальной доверенной настройке станции. В v1 нет команды получения,
выдачи или смены токена; обычный Manager не получает автоматически доступ к
каталогу Windows LocalService или закрытому каталогу Android APK.

Не записывайте токен или целые аутентифицированные запросы в логи клиента.
Плеер не шифрует TCP: для недоверенной сети требуется внешний защищённый
туннель/VPN. Подключение `QSslSocket` непосредственно к этому порту не поддержано.

## 3. Обрамление сообщений и ограничения

Сериализуйте JSON компактно, без физических переводов строки внутри объекта,
затем добавьте **один байт LF**. Последовательность `\n` внутри JSON-строки —
экранированное содержимое, а не граница сообщения. Не добавляйте HTTP-заголовки,
длину перед сообщением или завершающий нулевой байт.

TCP не сохраняет границы сообщений. Один `readyRead` может содержать часть
JSON, один объект или несколько строк. Клиент накапливает **байты**, извлекает
все полные строки до LF и сохраняет неполный хвост. Декодирование/разбор JSON
выполняется после получения полной строки: многобайтовая кириллица тоже может
быть разделена между чтениями.

| Ограничение сервера | Значение и поведение |
| --- | --- |
| Размер одного запроса | Не более **1 048 576 байт вместе с LF**, после кодирования UTF-8 |
| Одновременно принятые соединения | 16; лишние закрываются без JSON-ответа |
| Простой соединения | Закрытие через 30 секунд без входящих данных; сервер сам ничего не посылает |
| Очередь | Не более 1000 записей |
| Один путь | Не более 4096 единиц UTF-16 (`QString::size()`), без NUL |
| Накопившийся исходящий буфер | Перед следующей командой сервер закрывает соединение, если ожидает отправки более 8 MiB |

Лимит 1 MiB относится **к запросу**, а порог 8 MiB — **к накопившемуся буферу
отправки**. Они не задают максимальную длину одного ответа. Ответ всегда может
содержать всю очередь, в том числе собранную несколькими `enqueue`, и быть больше
1 MiB. Для клиента рекомендуется собственный предел **32 MiB на одну строку
ответа**, с проверкой размера полной строки и неполного хвоста. Это защитная
политика клиента, а не отдельная гарантия сервера.

Сервер не отправляет приветствие. После установления TCP клиент сам отправляет
`status`. Несколько команд в одном соединении допустимы; ответы в нём идут в
порядке запросов. Общего порядка между разными соединениями клиенту не обещано.
Все подключения управляют одним и тем же состоянием плеера.

## 4. Конверт запроса и ответа

### Запрос

```json
{"protocolVersion":1,"id":"req-001","token":"<CONTROL_TOKEN>","command":"status"}
```

В примерах `<CONTROL_TOKEN>` нужно заменить реальным токеном. После каждого
показанного объекта на проводе должен идти LF.

| Поле | Тип | Обязательность и смысл |
| --- | --- | --- |
| `protocolVersion` | number | Обязательно, значение `1` |
| `token` | string | Обязательно в каждом запросе, точное совпадение с токеном плеера |
| `command` | string | Обязательно, имя одной из 13 команд с учётом регистра |
| `id` | string / number / null | Необязательно; корректное значение возвращается в ответе |
| Поля команды | Зависит от команды | На том же уровне, что `command`; объекта `params` нет |

Для Manager используйте уникальные **строковые** `id`, например UUID или
`session-id:counter`. Объект, массив или boolean в `id` недопустимы. Если `id`
не передан, поле отсутствует и в ответе. `id` нужен только для сопоставления:
**повтор запроса с тем же `id` выполняет команду повторно**.

Неизвестные поля запроса отклоняются. Числа передаются JSON-числами, логические
значения — `true`/`false`; строки `"70"`, `"true"` не заменяют соответствующие типы.
Поля, для которых нет значения, следует опускать, а не отправлять как `null`.

### Успешный ответ

Начальное состояние нового процесса:

```json
{
  "protocolVersion": 1,
  "id": "req-001",
  "ok": true,
  "status": {
    "state": "stopped",
    "playbackRequested": false,
    "queue": [],
    "currentIndex": -1,
    "currentTrack": "",
    "positionMs": 0,
    "durationMs": 0,
    "volumePercent": 100,
    "muted": false,
    "repeat": "off",
    "error": ""
  }
}
```

Ответы здесь отформатированы для чтения; сервер отправляет их одной строкой.
Каждая успешная команда возвращает `ok: true` и полный `status`.

**`ok: true` подтверждает обработку команды.** Декодирование и запуск вывода
асинхронны. В ответе на `play` допустим `loading` и даже `error`, если ошибка
устройства обнаружена синхронно; поздняя ошибка появится в следующем `status`.
Не включайте индикатор звучания только по отправке команды или `ok: true`.

### Ошибочный ответ

Пример ошибки доступа:

```json
{"protocolVersion":1,"id":"req-002","ok":false,"error":{"code":"unauthorized","message":"Invalid control token."}}
```

Ошибки обработки команд движком также содержат полный `status`. Например:

```json
{
  "protocolVersion": 1,
  "id": "req-003",
  "ok": false,
  "error": {
    "code": "empty_queue",
    "message": "The playback queue is empty."
  },
  "status": {
    "state": "stopped",
    "playbackRequested": false,
    "queue": [],
    "currentIndex": -1,
    "currentTrack": "",
    "positionMs": 0,
    "durationMs": 0,
    "volumePercent": 100,
    "muted": false,
    "repeat": "off",
    "error": ""
  }
}
```

Обрабатывайте `error.code` программно; `message` — текст диагностики, его
формулировка не является стабильным идентификатором. Сетевое соединение может
закрыться и без JSON-ответа.

## 5. Все команды

К каждому примеру ниже добавляйте обязательные `protocolVersion` и `token`, а
также строковый `id`. Это **поля тела запроса**, показанные без общего конверта.

| Команда | Поля тела запроса | Результат |
| --- | --- | --- |
| `status` | `{"command":"status"}` | Прочитать состояние |
| `load` | `{"command":"load","paths":["/srv/music/a.wav","/srv/music/b.mp3"],"startIndex":0,"autoplay":false}` | Заменить очередь и выбрать запись |
| `enqueue` | `{"command":"enqueue","paths":["/srv/music/c.flac"]}` | Добавить записи в конец |
| `play` | `{"command":"play"}` | Запустить/продолжить выбранную запись |
| `pause` | `{"command":"pause"}` | Приостановить или отменить ожидаемый старт |
| `stop` | `{"command":"stop"}` | Остановить и перемотать в начало |
| `next` | `{"command":"next"}` | Выбрать следующую запись |
| `previous` | `{"command":"previous"}` | Выбрать предыдущую запись |
| `seek` | `{"command":"seek","positionMs":15000}` | Запросить позицию в миллисекундах |
| `volume` | `{"command":"volume","value":70}` | Громкость 0–100 |
| `mute` | `{"command":"mute","value":true}` | Включить/выключить отключение звука |
| `repeat` | `{"command":"repeat","mode":"all"}` | `off`, `all` или `one` |
| `clear` | `{"command":"clear"}` | Остановить и очистить очередь |

### `load` и `enqueue`: файлы и очередь

`paths` обязателен: непустой массив строк с абсолютными путями **на машине
плеера**. Путь на машине Manager не преобразуется и файл не пересылается.
До команды медиафайл должен быть размещён в доступном плееру каталоге.

Примеры путей: Windows — `C:/Media/music/Песня.mp3`, Linux —
`/srv/music/Песня.mp3`, Android — абсолютный путь внутри доступного APK каталога.
При использовании Windows-обратных слешей их нужно экранировать средствами
JSON-сериализатора. Не передавайте `file://`, `http://`, `content://`, относительные
пути, каталог вместо файла или NUL. Плеер проверяет наличие обычного файла и
доступ на чтение от имени своей учётной записи. Расширение и поддержка кодека
этой проверкой не подтверждаются: декодирование выполняется позже.

Общий предел очереди — 1000 записей. Одинаковый файл может входить несколько
раз; позиции таких записей различаются. Возвращаемые пути нормализуются через
`QDir::cleanPath`, поэтому Manager должен принимать очередь из ответа как
фактическую, а не требовать побайтового равенства исходным строкам.

`load`:

- `startIndex` необязателен, целое от 0 до `paths.length - 1`, по умолчанию 0.
- `autoplay` необязателен, boolean, по умолчанию false.
- Все пути и параметры проверяются до замены очереди. Ошибка валидации сохраняет
  прежнюю очередь и воспроизведение.
- Успешный `load` всегда заменяет очередь, выбирает запись и сбрасывает её
  позицию. Без `autoplay: true` воспроизведение не начинается, даже если до этого
  музыка играла. Команда не является бесшовным редактированием текущей очереди.
- Пустой массив запрещён; используйте `clear`.

`enqueue`:

- Дополнительные поля `startIndex` и `autoplay` не разрешены.
- Все добавляемые пути проверяются до изменения очереди, включая общий лимит.
- В непустой очереди не меняет текущую запись/позицию и не запускает музыку.
- В пустой очереди выбирает запись 0 без автозапуска; для старта нужен `play`.

Громкость, mute и режим повтора сохраняются при `load`, `enqueue`, `stop`, `clear`.

### Воспроизведение, пауза и остановка

`play` запускает выбранную запись; после паузы продолжает её. После ошибки
плеер заново пробует загрузить выбранный файл. Пустая очередь даёт `empty_queue`.
Повторный `play` не следует использовать как heartbeat.

`pause` снимает намерение воспроизводить. Для уже играющего трека backend
подтверждает `paused`. Если старт ещё был в `loading`, он отменяется и состояние
может стать `stopped`. Пауза пустой очереди допустима.

`stop` сохраняет очередь и выбранный индекс, устанавливает позицию 0 и очищает
сообщение ошибки. Известная длительность может сохраниться. Пустая очередь
допустима. TCP-сервер продолжает работать.

`clear` дополнительно сбрасывает очередь, индекс в −1, путь в пустую строку,
позицию и длительность в 0. Громкость, mute и repeat сохраняются.

### Навигация и повтор

`next` и `previous` требуют непустую очередь. Если было запрошено воспроизведение,
новая запись запускается. При навигации с паузы или остановки новая запись
выбирается в состоянии `stopped` с позиции 0.

| Ситуация | `off` | `all` | `one` |
| --- | --- | --- | --- |
| Естественное окончание непоследней записи | Следующая | Следующая | Та же с начала |
| Естественное окончание последней записи | Остановка на последней | Первая | Та же с начала |
| Ручной `next` на последней записи | Остановка, позиция 0, индекс сохранён | Первая | Как `off` |
| Ручной `previous` на первой записи | Первая с начала | Последняя с начала | Как `off` |

В остальных случаях ручная навигация меняет индекс на +1/−1. Индексы нулевые.
`previous` не имеет поведения «сначала перемотать текущую песню, если прошло
несколько секунд»: он выбирает предыдущую запись сразу.

При естественном окончании очереди в `off` индекс остаётся последним, а позиция
может остаться в конце трека. Это отличается от явной команды `stop` с позицией 0.

### Позиция, громкость, mute

`seek.positionMs` — целое JSON-число от 0 до **9 007 199 254 740 991**.
Если известна положительная `durationMs`, позиция выше неё отклоняется.
При неизвестной длительности сервер не проверяет верхнюю границу по треку.
Пустая очередь даёт `empty_queue`. Успешный ответ подтверждает передачу запроса
backend; фактическую позицию берите из последующих состояний. Seek не включает
воспроизведение автоматически; поддержка перемотки зависит от backend/файла.

`volume.value` — целое JSON-число 0–100, `mute.value` — boolean. Эти команды
разрешены без очереди. Mute не меняет сохранённый `volumePercent`.

### Ошибки аудио после принятия очереди

Если файл исчез после `load` либо декодер сообщил ошибку, плеер при запрошенном
воспроизведении пробует следующие записи. Для `all` разрешён переход к началу,
но уже неудачные записи в этой цепочке попыток повторно не выбираются. Для `off`
и `one` после ошибки поиск идёт только вперёд до конца. `one` не зацикливает
повреждённый файл.

Когда подходящих записей не осталось, состояние — `error`, а
`playbackRequested: false`. При успешном выборе следующего трека сообщение
предыдущей ошибки может очиститься. Polling может пропустить краткую ошибку:
API v1 не является полным журналом проигрывания.

## 6. Объект `status`

| Поле | Тип | Значение |
| --- | --- | --- |
| `state` | string | `stopped`, `loading`, `playing`, `paused`, `error` |
| `playbackRequested` | boolean | Намерение воспроизводить; true также во время загрузки и переходов |
| `queue` | array of string | Полная общая очередь абсолютных путей в порядке воспроизведения |
| `currentIndex` | integer | Индекс выбранной записи с 0; −1 при пустой очереди |
| `currentTrack` | string | Путь выбранной записи, пустая строка при пустой очереди |
| `positionMs` | integer | Последняя сообщённая позиция backend в миллисекундах |
| `durationMs` | integer | Длительность в миллисекундах; 0, если пока неизвестна |
| `volumePercent` | integer | 0–100, по умолчанию 100 |
| `muted` | boolean | По умолчанию false |
| `repeat` | string | `off`, `all`, `one`; по умолчанию `off` |
| `error` | string | Последнее текущее сообщение ошибки аудио; пустая строка при его отсутствии |

`playing` означает подтверждение от аудиобэкенда. `currentTrack` показывает
выбранный файл также на паузе и при остановке. Он сам по себе не означает,
что файл звучит. Громкость 0, mute, отключённый усилитель и системная маршрутизация
звука не определяются одним значением `state`.

`state: stopped` кратковременно возможен при `playbackRequested: true` между
окончанием одного трека и запуском следующего. `state: error` при true возможен
во время попытки перейти к следующему файлу. Не пытайтесь автоматически
«исправлять» эти состояния командами `play` или `load`.

Состояние соединения Manager хранит отдельно: «Нет связи» не равно
`state: stopped`. После обрыва последний полученный `status` — устаревший снимок,
а реальное воспроизведение может продолжаться.

## 7. Ошибки протокола и команд

| `error.code` | Причина | `id` / `status` в ответе |
| --- | --- | --- |
| `invalid_json` | Невалидный JSON или корневое значение не объект | Оба отсутствуют |
| `request_too_large` | Слишком большая строка/незавершённый запрос | Оба отсутствуют; затем соединение закрывается |
| `invalid_request` | Недопустимый тип `id` | Оба отсутствуют |
| `unauthorized` | Токен отсутствует, неверен или имеет неправильный тип | Корректный `id` возвращается; `status` нет |
| `unsupported_protocol` | После успешной аутентификации версия отсутствует или не равна числу 1 | Корректный `id` возвращается; `status` нет |
| `invalid_request` | `command` отсутствует или не строка | Корректный `id` возвращается; полный `status` есть |
| `unknown_command` | Строковое имя команды не поддержано | Корректный `id` возвращается; полный `status` есть |
| `invalid_arguments` | Неверный тип/диапазон, лишнее поле, пустой/слишком большой список | Корректный `id` возвращается; полный `status` есть |
| `invalid_path` | Неверный, недоступный путь или путь не к обычному читаемому файлу | Корректный `id` возвращается; полный `status` есть |
| `empty_queue` | `play`, `next`, `previous` или `seek` без выбранной записи | Корректный `id` возвращается; полный `status` есть |

Если запрос не содержал `id`, возвращать нечего — поле отсутствует. Не выводите
наличие `status` только из имени кода: у `invalid_request` есть два разных случая.
Большинство ошибок оставляют соединение открытым. Разрыв по idle timeout,
лимиту подключений или медленному чтению может не содержать ответ вообще.

Верхнеуровневый `error` описывает отказ выполнить команду, а `status.error` —
состояние аудио. Например, успешный запрос `status` может иметь `ok: true` и
`status.state: error`.

## 8. Переподключение и неоднозначный результат

Разрыв соединения не останавливает музыку, не сбрасывает очередь и не отменяет
уже выполненную команду. После восстановления связи первым запросом отправляйте
`status` и принимайте полученное состояние как фактическое.

Если запрос был отправлен, а ответ потерян, клиент не знает, выполнилась ли
команда. TCP и `id` не дают гарантии выполнения ровно один раз. Например,
автоматический повтор `enqueue` может добавить файлы дважды, `next` — пропустить
ещё одну запись, `load` — повторно сбросить текущий трек.

Для клиента первой версии **автоматически повторяется только чтение `status`**.
Результат неподтверждённой изменяющей команды обозначается как неизвестный.
После переподключения прочитайте состояние; новое изменяющее действие требует
актуального намерения пользователя. Даже полученный `status` не доказывает
выполнение конкретного потерянного запроса.

При отключении отмените неотправленные команды клиента и сообщите вызывающему
коду об отмене. Очистите неполную входящую строку и таблицу ожидаемых ответов.
События старого сокета не должны менять состояние нового соединения.

При **перезапуске процесса** очередь, позиция, громкость, mute и repeat сбрасываются
в начальные значения; токен сохраняется. В протоколе нет идентификатора запуска,
поэтому пустая очередь сама по себе не доказывает перезапуск. Не отправляйте
сохранённую очередь автоматически после каждого подключения. Восстановление
программы станции должно быть отдельной явной политикой Manager.

## 9. Рекомендуемая реализация клиента на Qt

Это требования к новому клиенту, а не дополнительные возможности сервера.

1. Создайте отдельный `QObject`, например `MediaBoxPlayerClient`, с `QTcpSocket`,
   байтовым входным буфером, таймерами подключения/ответа/polling и очередью команд.
   Добавьте клиентскому target зависимость `Qt6::Network`.
2. Предоставьте настройку `host`, `port`, `token`, методы connect/disconnect и
   методы для всех 13 команд. Работа с сокетом выполняется в его Qt-потоке.
3. Используйте асинхронные `connected`, `readyRead`, `disconnected`, `errorOccurred`
   и `QTimer`. `waitForConnected`/`waitForReadyRead` в потоке интерфейса запрещены.
4. После `connected` отправьте `status`. Считайте клиент готовым только после
   корректного ответа с `protocolVersion: 1`, ожидаемым `id`, `ok: true` и валидным
   `status`. На `unauthorized` или несовместимую версию остановите автоматические
   попытки до изменения настроек или явного повторного подключения.
5. Для первой реализации держите **один неподтверждённый запрос** на соединение.
   Новые действия ставьте в очередь; polling не должен создавать очередь
   одинаковых `status` или задерживать пользовательские команды.
6. Формируйте запрос `QJsonDocument::Compact`, кодируйте в UTF-8, добавляйте LF,
   проверяйте длину и отправляйте через `QTcpSocket::write`. Отслеживайте локальный
   отказ записи; попадание данных в буфер сокета не является подтверждением команды.
7. В `readyRead` выделяйте полные строки и проверяйте JSON-объект, типы полей,
   версию, `id` и структуру состояния. Неразбираемый ответ, невозможное состояние
   или несопоставимый `id` считайте ошибкой протокола: закройте соединение и
   сверяйтесь заново через `status` без повторения мутаций. При корректной версии
   дополнительные поля ответа можно игнорировать; неизвестные значения enum
   не следует отображать как известное состояние.
8. Получайте `status` раз в **1000 мс**, пока соединение готово и нет ожидаемого
   ответа. Это рекомендуемый интервал клиента, не серверная настройка. Он даёт
   обновления и поддерживает соединение активным при серверном idle timeout 30 с.
9. Разумные стартовые таймауты клиента: подключение **3 с**, ответ **5 с**.
   Они настраиваемы; сервер не обещает максимальное время работы файлового ввода.
   На timeout ответа закройте сокет и обработайте неопределённый исход по разделу 8.
10. При сетевых сбоях переподключайтесь с задержками **1, 2, 4, 8, 16, 30 с**,
    затем не чаще раза в 30 с; небольшой случайный разброс допустим. Явное
    отключение пользователем отменяет retries. После успеха сбрасывайте задержку.
11. Передавайте наружу независимо: состояние соединения, принятый `status`,
    результат команды по `id`, отказ команды и неизвестный результат после обрыва.
    Для UI используйте данные плеера. Локальная анимация позиции допустима только
    как оценка с последующей сверкой; VU/метаданных обложки в API нет.
12. Объединяйте ещё не отправленные промежуточные изменения ползунка громкости
    или seek, если это необходимо. Уже отправленные команды нельзя считать
    отменёнными. При смене адреса/токена закрывайте старое соединение, отменяйте
    очередь и начинайте новую сессию с `status`.

Последовательность подключения и запуска подготовленной очереди:

```text
Manager                              Player
   |------ TCP connect ---------------->|
   |------ status, id=s1 --------------->|
   |<----- ok, status, id=s1 ------------|
   |      клиент готов                  |
   |------ load, autoplay=false, id=l1 ->|
   |<----- ok, status, id=l1 ------------|
   |------ volume, value=70, id=v1 ----->|
   |<----- ok, status, id=v1 ------------|
   |------ play, id=p1 ----------------->|
   |<----- ok, status, id=p1 ------------|
   |------ status, id=s2 --------------->|
   |<----- актуальный status, id=s2 -----|
```

Громкость и mute при необходимости установите **до** `play` или `load` с
`autoplay: true`, чтобы начало трека не прозвучало с прежними настройками.

### Точки подключения существующего Manager

Старое управление находится в `src/mediacontroller.cpp` репозитория Manager.
При реализации интеграции используйте следующие соответствия:

| Существующее действие | Поведение для нового плеера |
| --- | --- |
| `MediaController::play()` | TCP `play`; при пустой очереди сначала нужен явный выбор/загрузка очереди |
| `MediaController::stop()` | TCP `stop`, служба продолжает работу |
| `isPlaying()` / `sendPlayingState()` | Последний подтверждённый `status` плюс отдельный признак актуальности соединения; асинхронный опрос по TCP |
| `playTrack(path)` | Если действие означает замену программы выбранным файлом — `load` с одним путём и `autoplay: true`; такая замена уничтожает прежнюю очередь, автоматического возврата нет |
| `refreshPlayer()` | Прямого аналога в API нет. Изменение очереди выполняется явными `load`/`enqueue`; не подменяйте обновление экрана командой `load` |
| `showPlayer()` / `hidePlayer()` и соответствующие slots | У нового плеера нет окна и таких сетевых команд; не отправляйте `show`/`hide` |

Синхронный `bool` от старого запуска процесса не может подтверждать воспроизведение
нового плеера. Перенесите уведомление UI на асинхронные ответы клиента. Настройки
подключения сохраняйте штатным механизмом Manager; INI/реестр не должны служить
каналом команд или источником фактического состояния плеера.

## 10. Минимальная диагностическая проверка

Этот Python 3 пример делает только `status`. Он показывает реальное обрамление,
таймауты и корреляцию; для GUI-клиента используйте асинхронный алгоритм выше.
Перед запуском задайте `MEDIABOX_TOKEN`; `MEDIABOX_HOST` и `MEDIABOX_PORT`
необязательны. Токен в вывод не попадает.

```python
import json
import os
import socket
import uuid

host = os.environ.get("MEDIABOX_HOST", "127.0.0.1")
port = int(os.environ.get("MEDIABOX_PORT", "17655"))
token = os.environ["MEDIABOX_TOKEN"].strip()
request_id = str(uuid.uuid4())
request = {
    "protocolVersion": 1,
    "id": request_id,
    "token": token,
    "command": "status",
}
frame = json.dumps(request, ensure_ascii=False, separators=(",", ":")).encode("utf-8") + b"\n"
if len(frame) > 1024 * 1024:
    raise ValueError("Request is too large")

with socket.create_connection((host, port), timeout=3) as connection:
    connection.settimeout(5)
    connection.sendall(frame)
    with connection.makefile("rb") as incoming:
        limit = 32 * 1024 * 1024  # Client policy, not a protocol frame limit.
        line = incoming.readline(limit + 1)
        if len(line) > limit or not line.endswith(b"\n"):
            raise RuntimeError("Incomplete or oversized reply")
        reply = json.loads(line.decode("utf-8"))
        if not isinstance(reply, dict) or reply.get("protocolVersion") != 1 or reply.get("id") != request_id:
            raise RuntimeError("Unexpected protocol version or request id")
        if reply.get("ok") is not True:
            raise RuntimeError(reply.get("error", "Command rejected"))
        if not isinstance(reply.get("status"), dict):
            raise RuntimeError("Missing player status")
        print(json.dumps(reply["status"], ensure_ascii=False, indent=2))
```

## 11. Критерии приёмки клиента

Проверяйте клиент как с управляемым тестовым TCP-сервером, так и с запущенным
MediaBoxPlayer. Тестовый сервер нужен для воспроизводимых обрывов и задержек.

| Сценарий | Ожидаемое поведение Manager |
| --- | --- |
| Успешное подключение | Сам отправляет `status`; готовность только после ответа |
| Полный цикл всех 13 команд | Правильные поля, типы, `id`; результат отображается по ответам |
| JSON/кириллица разбиты на несколько чтений | Ответ собирается без потерь и ошибок кодировки |
| Несколько ответов в одном чтении обработчика транспорта | Все строки разбираются, хвост сохраняется; `id` проверяется |
| Неверный токен/версия | Понятная ошибка подключения; нет бесконечных повторов |
| Пустая очередь, неверный путь, лишнее поле | Ошибка команды и актуальное состояние обрабатываются раздельно |
| `play` ответил `ok` с `loading`/`error` | UI не показывает неподтверждённое воспроизведение |
| Воспроизведение продолжается без Manager | После reconnect состояние считывается, очередь не загружается заново |
| Сервер применил `enqueue`/`next` и закрыл соединение до ответа | Нет автоматического повтора; исход отмечен неизвестным |
| Idle больше 30 с/пропал сервер | Клиент замечает разрыв/timeout, UI остаётся отзывчивым |
| Сервер вернул большой `status` > 1 MiB | Клиент читает его в пределах своей политики, не применяет лимит запроса к ответу |
| Слишком длинный/повреждённый ответ | Буфер ограничен, соединение закрывается без зависания |
| Сменились настройки или пользователь отключился | Старые таймеры/ответы не влияют на новую сессию |
| Повторное подключение к перезапущенному процессу | Принимается его начальное состояние; не делается вывод о старой очереди |
| `stop`, затем `play` | Используется тот же TCP-сервер; служба ОС не останавливается |

В логах тестов и приложения не должно быть токена. Проверки клиента не требуют
переопределять протокол или добавлять серверные команды, которых пока нет.
