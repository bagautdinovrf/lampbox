# Формат расписания MediaBoxManager и MediaBoxPlayer

Проект спецификации версии 1 от 3 октября 2026 года. MediaBoxManager редактирует календарные правила и публикует цельный снимок расписания. MediaBoxPlayer принимает снимок и выбирает треки по этим правилам. Главный сценарий — обычная программа с новогодним плейлистом через один трек, без копирования основного расписания.

Это предложение контракта, а не реализованный парсер или исполнитель. Схемы и примеры предназначены для проверки и дальнейшей реализации. Примерные медиафайлы и особые даты клиента демонстрационные; календарь не является официальным перечнем праздников.

## Файлы и источники данных

| Хранилище | Назначение | Кто изменяет |
| --- | --- | --- |
| `project.sqlite` | Редактируемые правила, шаблоны, плейлисты, календари, черновики и выпуски | MediaBoxManager |
| `snapshots/<publicationId>.json` | Неизменяемый снимок для воспроизведения | MediaBoxManager при публикации |
| `active.json` | Указатель на выбранный выпуск и SHA-256 его байтов | MediaBoxManager при публикации |
| `runtime.sqlite` | Фаза чередования, курсоры, история запусков, принятый выпуск | MediaBoxPlayer |

SQLite — единственный источник редактируемого проекта. JSON-снимок можно импортировать после проверки в новый черновик; он не синхронизируется с БД в обе стороны. На первом этапе допускается один редактируемый JSON с одним писателем, если контракт публикации остаётся тем же. SQLite позволяет сохранять несколько связанных изменений транзакцией; это основание выбора, а не обязательное требование к первой реализации. См. [транзакции SQLite](https://sqlite.org/lang_transaction.html).

Файлы контракта записываются в UTF-8 без BOM. Повторяющиеся ключи объектов запрещены. Порядок ключей и порядок массивов правил не влияют на исполнение. Порядок `entries` и `pattern` имеет смысл. Неподдерживаемая версия, тип правила или неизвестное поле приводят к отказу от нового выпуска с сохранением предыдущего рабочего.

В каталоге находятся [схема расписания](schedule.schema.json), [схема указателя](active.schema.json), [новогодний пример](example.new-year.json) и [указатель на пример](example.active.json).

## Идентификаторы и версии

| Поле | Значение |
| --- | --- |
| `format` | Всегда `mediabox.schedule` |
| `schemaVersion` | Версия структуры и семантики контракта, в этом проекте `1` |
| `scheduleId` | Постоянный UUID проекта расписания |
| `stationId` | UUID станции, для которой предназначен выпуск |
| `publicationId` | Новый UUID каждого выпуска, включая повторную публикацию старого содержимого |
| `revision` | Возрастающий номер выпуска одного расписания, целое от 1 до 2147483647 |
| `publishedAt` | Момент выпуска в UTC, например `2026-10-03T09:00:00Z` |
| `timeZone` | Идентификатор часового пояса станции, например `Europe/Moscow` |
| `validity` | Диапазон дат, на который выпуск полностью проверен |
| `requiredCapabilities` | Требуемые возможности плеера: `calendar.v1`, при необходимости `rotation.strict.v1` и `events.fixed.v1` |

UUID имеют строчную запись с дефисами. ID медиафайла, записи плейлиста, плейлиста, календаря, шаблона, временного слота и правила стабильны. Название, путь и индекс в массиве ID не заменяют. Все ID сущностей внутри снимка уникальны, включая записи разных плейлистов.

`revision` выпуска, `revision` плейлиста и `schemaVersion` независимы. Ревизия плейлиста увеличивается при изменении состава, порядка или алгоритма выбора; переименование не требует сброса курсора. Откат выполняется новым выпуском с большим номером. Внутренние версии схем БД Manager и Player тоже независимы от версии JSON.

Массивы обязательны; отсутствие правил обозначается пустым массивом. Необязательная граница `range` целиком отсутствует при отсутствии ограничения. Значения `null`, строки вместо чисел, специальные строки `*`, `15m` и выполняемые выражения в новом формате не используются.

## Каталог контента

Снимок содержит `assets` и `playlists`, необходимые для автономной работы станции. Медиафайл задаётся `id`, `path` и `mediaType: audio`. Пути используют `/` и разрешаются относительно настроенного каталога контента MediaBoxPlayer. Абсолютные пути Windows, обратные слеши и сегменты `.` или `..` запрещены. После разрешения ссылок итоговый путь должен оставаться внутри каталога контента.

Плейлист содержит `id`, `revision`, отображаемое `name`, `order` и массив `entries` с собственными ID и ссылками `assetId`. Один файл может входить в несколько списков либо несколько раз в один список. Это разные записи с разными курсорами. Пустой плейлист допускается и обрабатывается политикой отсутствующего контента.

`sequential` выбирает записи по порядку и начинает новый круг после последней. `shuffle_cycle` перемешивает записи на круг, проигрывает каждую доступную запись один раз и создаёт следующий круг. Состав текущего перемешанного круга сохраняется в runtime. Общая защита от повторов одного файла между разными плейлистами в v1 не обещается.

Состав плейлиста зафиксирован выпуском. Автоматическое сканирование папки и добавление новых файлов не меняют уже принятый снимок. Обновлённая медиатека требует публикации. Аудиобайты находятся отдельно; перенос файла с сохранением ID обновляет его путь в следующем выпуске.

## Даты и календарные условия

Все даты записываются как `YYYY-MM-DD` с реальным годом. Локальное время имеет вид `HH:mm:ss`. Дни недели — ISO: понедельник 1, воскресенье 7. Диапазоны `validity`, `coverage` и `range` используют включённое `from` и исключённое `until`. Для периода с 15 декабря 2026 по 15 января 2027 включительно хранится `from: 2026-12-15`, `until: 2027-01-16`.

`when` содержит одно условие `select`, необязательный диапазон `range` и обязательный массив `excludeDates`. Совпадение означает: дата соответствует `select`, входит в `range`, если он задан, и отсутствует в `excludeDates`. Все эти проверки соединены логическим И. Несколько условий ИЛИ выражаются отдельными правилами или одним календарём.

| Тип `select` | Значение |
| --- | --- |
| `all` | Каждый день |
| `weekdays` | Один из дней массива `days` |
| `dates` | Одна из конкретных дат массива `dates` |
| `calendar` | Дата входит в календарь по `calendarId` |
| `annual_filter` | Месяц, день месяца и день недели входят в соответствующие массивы; фильтр повторяется ежегодно |

`annual_filter` сохраняет старые повторяемые условия месяцев и чисел без подстановки текущего года. Несуществующая дата, например 31 февраля, не создаёт вхождение. Для сезонного новогоднего периода через год в первом варианте используются явные даты `range`; составление следующих сезонных периодов — операция редактора, создающая отдельные правила. Полный произвольный RRULE в v1 не входит.

Календарь — именованный набор дат с `id`, `revision` и `coverage`. Рабочие дни с перенесёнными субботами, праздники и локальные даты клиента могут быть разными календарями. За пределами `coverage` результат неизвестен: публикация требует покрытия всего `validity` каждым используемым календарём. Уже принятый выпуск не получает праздники из сети; обновление календаря публикуется явно.

Выпуск вне `validity` считается истёкшим. При следующем выборе трека применяется `fallback`, правила и события больше не исполняются; Player сообщает об истечении. Manager должен продлевать проверенный период заранее. Запись `until` в интерфейсе можно показывать как последний включённый день, сохраняя указанную семантику файла.

## Шаблоны дня и базовые правила

`dayTemplates` содержит наборы временных слотов. Каждый слот задаёт `window`, источник `source` и `volumePercent`. Источник — `{type: playlist, playlistId: ...}` либо `{type: silence}`. Явная тишина запрещает праздничное подмешивание в этом интервале и не заменяется резервным списком.

Окно задаётся `from`, `until` и `untilDayOffset` 0 или 1. Начало включено, конец исключён. Например, `22:00:00` → `02:00:00`, смещение 1, — четыре часа. `00:00:00` → `00:00:00`, смещение 1, — полный день. Нулевая длительность, отрицательная длительность и длительность больше суток запрещены. Смежные интервалы `08:00–12:00` и `12:00–18:00` не пересекаются.

Календарное условие проверяется на дате начала окна. Окно пятницы `22:00–02:00` продолжается в субботу, даже если суббота не входит в условие. При поиске активного окна учитываются текущая и предыдущая даты. `validity` ограничивает итоговый интервал независимо от ночного продолжения.

`baseRules` назначает шаблон дня по `when`. Приоритет — явное целое число, большее значение выигрывает. Кандидат существует только там, где совпали дата и слот его шаблона. Вне слотов более приоритетного шаблона может действовать менее приоритетное правило. Для замены всего дня шаблон обязан покрывать весь день, включая явную тишину при необходимости.

Для базовых правил и правил подмешивания победитель выбирается раздельно. Одинаковый приоритет пересекающихся кандидатов в одной группе — ошибка публикации; порядок массива не решает конфликт. Пересекающиеся слоты внутри одного шаблона и окна одного mix-правила тоже запрещены. Специальная дата не получает скрытый приоритет: редактор выставляет его явно, например 10 для обычной программы, 20 для выходного дня и 100 для исключения на дату.

`fallback` содержит источник и громкость. Он применяется, если нет базового кандидата или выбранный базовый плейлист не имеет доступных записей. Резервный плейлист в таком случае является текущим базовым источником. Если резерв тоже недоступен, наступает тишина с диагностикой. Циклы резервов невозможны: в v1 задаётся один резервный источник.

## Подмешивание праздничного плейлиста

`mixRules` хранит `when`, временные `windows`, приоритет и буквальный массив источников `pattern`. В v1 выигрывает одно активное правило подмешивания. Первый слот — `{type: active_base}`; хотя бы один последующий слот ссылается на плейлист. `active_base` каждый раз разрешается по текущему базовому расписанию.

Пример фрагмента новогоднего правила:

```json
{
  "when": {
    "select": { "type": "all" },
    "range": { "from": "2026-12-15", "until": "2027-01-16" },
    "excludeDates": []
  },
  "pattern": [
    { "type": "active_base" },
    { "type": "playlist", "playlistId": "00000000-0000-4000-8000-000000000203" }
  ]
}
```

Это основной трек → праздничный → основной → праздничный. Для двух основных перед одним праздничным `active_base` повторяется дважды. Вероятность 50 процентов не заменяет строгую последовательность. Громкость дополнительного трека наследуется от эффективного базового слота или резерва.

Фаза принадлежит mix-правилу, курсор — конкретному плейлисту. Смена «Утро» → «День» сохраняет фазу и берёт курсор нового основного списка. Если календарное правило полностью заменило базовую программу, подмешивание продолжает использовать её как `active_base`. Исключение, которое должно отключить подмешивание, явно добавляется в `excludeDates` или изменяет само mix-правило.

Все музыкальные изменения применяются перед следующим треком: `musicTransition: finish_track`. Текущий трек доигрывает. Новая непрерывная активация mix-правила начинается с первого слота. Возврат после другого победившего mix-правила либо после реального разрыва периода является новой активацией. Полночь внутри непрерывного периода активацию не сбрасывает. Отсутствие доступной базы при всё ещё выбранном mix-правиле приостанавливает его фазу.

Успешно подтверждённое начало музыкального трека потребляет слот и продвигает курсор. Ошибка запуска этого не делает. Завершение и пропуск запрашивают следующий трек, но не потребляют слот повторно. Предварительная загрузка будущей очереди не продвигает состояние; после изменения правил ещё не начавшаяся очередь пересчитывается.

Если дополнительный список пуст или недоступен, `emptyAdditionalSource: use_base` подставляет основной трек. Его успешный запуск потребляет дополнительный слот; такое отклонение отражается в журнале. Если доступной базы нет, дополнительный плейлист сам её не создаёт. Рекламные события и отдельное ручное воспроизведение не меняют фазу ротации.

## Рекламные события

`eventRules` задаёт конкретные локальные `times` в подходящие даты `when`. `action` ссылается на один `assetId` и задаёт громкость. `delivery.start: after_track` ждёт окончания текущего трека, а `interrupt` приостанавливает его. `maxLateSeconds` ограничивает задержку относительно запланированного момента; просроченное событие пропускается. После события возобновляется приостановленный трек с сохранённой позиции либо выбирается следующий музыкальный трек, если приостановленного нет.

Возобновление не считается новым потреблением музыкального слота. Одно рекламное событие не прерывает другое: готовые события сортируются по убыванию приоритета, затем по запланированному UTC-моменту и ID правила. Событие исполняется один раз для пары `ruleId` и запланированного UTC-момента внутри `scheduleId`. Перепубликация не создаёт его повторно.

Время преобразуется в зоне станции. `timeResolution.gap: skip` пропускает несуществующий локальный момент; `overlap: first` выбирает первый из двух повторяющихся моментов. Окно с несуществующей границей пропускается целиком, с неоднозначной границей использует первое вхождение. Диагностика сообщает о пропуске. В v1 один аудиовыход; независимые зоны и видео требуют следующего согласованного расширения.

Частота N раз в час и распределение по свободным местам вычисляются редактором в конкретные `times` до публикации. Для сохранения исходной настройки Manager может хранить её в своём проекте. Исполнитель не переопределяет минуты случайно при запуске. События «через N минут после другого события» и произвольные сценарии пока не входят в v1.

## Состояние MediaBoxPlayer

В `runtime.sqlite` хранятся принятый `publicationId`, подтверждённые запуски, активное mix-правило и его непрерывная активация, отпечаток `pattern`, следующий слот, курсоры плейлистов, непроигранная часть перемешанного круга и состояния рекламных вхождений.

Новая публикация не обнуляет состояние автоматически. При сохранении ID, шаблона чередования и непрерывного действия правило сохраняет фазу. Изменение `pattern` или начало новой активации возвращает первый слот. Переименование не влияет на исполнение. После изменения последовательного списка сохранившаяся последняя запись позволяет продолжить после неё в новом порядке; если запись удалена, выбор начинается с первой доступной. Перемешанный круг сохраняет оставшиеся ID, удаляет исчезнувшие; добавленные записи включаются в следующий круг.

Повторные уведомления о начале одного `playbackId` обрабатываются один раз. Для рекламного вхождения сохраняются состояния pending, starting, started, completed, failed, skipped. После аварии неоднозначное starting/started не переигрывается автоматически и отображается в диагностике. Аудиовыход и SQLite нельзя объединить одной транзакцией, поэтому гарантия ровно одного фактического звучания через аварии в этой версии не заявляется. Восстановление текущего музыкального трека и позиции относится к политике Player, отдельно от формата расписания.

## Проверка и публикация

JSON Schema Draft 2020-12 проверяет форму, типы, перечисления и обязательные поля. Проверка `format` должна быть явно включена. Ссылки между сущностями, уникальность ID, часовой пояс, реальные даты, границы интервалов, конфликты и возможности исполнителя проверяет отдельный семантический валидатор. См. [описание JSON Schema](https://json-schema.org/draft/2020-12) и [поведение проверки format](https://json-schema.org/draft/2020-12/json-schema-validation#section-7.2.1).

Перед выпуском Manager обязан проверить весь конечный `validity`, соседние даты для ночных окон, покрытие календарей, все ссылки, доступность зоны и явные приоритеты. `requiredCapabilities` выводится из фактических правил: календарь всегда, ротация при наличии mix-правил, события при наличии event-правил. Проверка готового снимка выполняется и Player; неизвестная возможность запрещает принятие. Отсутствующий аудиофайл диагностируется отдельно от структурной ошибки и обрабатывается резервом.

Порядок публикации:

1. В транзакции сохранить готовый выпуск, точные UTF-8 байты снимка и SHA-256 в `project.sqlite`.
2. Записать неизменяемый `snapshots/<publicationId>.json`, перечитать и проверить байты.
3. Атомарно заменить `active.json` с ID станции, расписания, выпуска, номером, относительным путём и SHA-256 снимка.
4. Player проверяет указатель, хеш, IDs, схему, семантику и возможности, затем подтверждает принятый выпуск. Для снимка повторная доставка того же ID и хеша идемпотентна; меньшая ревизия и совпавший ID с другими байтами отвергаются.
5. Новые музыкальные правила вступают перед следующим треком; обновлённые рекламные правила — после подтверждения принятия. Уже начавшееся событие завершается по предыдущему контексту.

`active.json` обозначает выбранный Manager выпуск. Фактическое принятие подтверждает ответ Player и его runtime, а не успешная запись указателя. Ошибка нового файла оставляет предыдущий принятый выпуск действующим в пределах его `validity`. SHA-256 считается от точных байтов без включения хеша внутрь снимка; специальная канонизация JSON не нужна.

Для записи внутренних файлов подходит `QSaveFile` с выключенным `directWriteFallback`: [документация Qt](https://doc.qt.io/qt-6/qsavefile.html). БД и файловая система не имеют общей атомарной транзакции. Сбой до смены указателя оставляет неактивный выпуск; после смены, но до подтверждения Player, Manager повторно сверяет состояние. При файловой ошибке нельзя помечать выпуск принятым.

UUID хранятся как TEXT, порядок как целый `ordinal`; внешние ключи и уникальные ограничения включаются явно. Связанные правки выполняются одной транзакцией. JSON условий хранит типизированные варианты этой спецификации. Ссылки внутри JSON проверяет семантический валидатор; только SQL foreign keys их не проверят. Удаление используемого плейлиста либо календаря блокируется до изменения ссылок. Таблицы Player размещаются в другой БД и принадлежат одному исполнителю станции.

## Переход со старого LampPlayer

Старые форматы — импорт и отдельный экспорт. Они не ограничивают новый контракт MediaBoxManager и MediaBoxPlayer. При импорте музыкальные строки разделяются на плейлист, шаблон и правило `annual_filter`; год не придумывается. Нумерацию дней недели, поведение пересечений и ночных окон нужно сверить с самим старым плеером, а неоднозначности показать пользователю.

Редактор уже хранит правила в версионированном `project.json` (`mediabox.manager-project`, версия 1) через `ProjectRepository`. Однократный `ScheduleImport` читает старые файлы только при отсутствии JSON и сохраняет оригиналы. Загрузка `ChannelManager::collectChannels()` не удаляет каналы или медиакаталоги. Некорректные данные диагностируются до замены состояния в памяти, а сохранение блокируется до успешной загрузки. Формат проекта редактора не является описанным здесь форматом исполняемых снимков.

Для однократного переноса рекламы источник — `advertView`, а `adverttable` содержит ранее назначенные минуты. Минутные строки `15m` и числовые частоты 1–5 разбираются в разные типы; `*` означает отключённую запись. Совпадающий с правилом набор опубликованных минут сохраняется в JSON; при его отсутствии общий доменный расчёт назначает воспроизводимые минуты. Дальнейшее редактирование использует только JSON.

Обратный экспорт в CSV/cron/XML удалён вместе со старыми генераторами. Публикация описанных в этом документе снимков и их исполнение плеерами требуют отдельной реализации.

## Границы первой версии

Первый вариант покрывает календарь, повторяемую недельную программу, конкретные даты и ежегодные фильтры, ночные окна, одно активное подмешивание с произвольным строгим pattern и рекламные события в фиксированное время. Следующими расширениями могут стать независимые аудиозоны, видео, композиция нескольких mix-правил, ограничение повторов между источниками и сложные правила повторения. Для изменения семантики выпускается новая версия контракта.
